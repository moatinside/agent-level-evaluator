## 1. 今回作るもの

**日々の会話評価に、問いの変化、ユーザーの介入、Agentの応答の順序を並べた確認材料を加える。ユーザーの訂正を記録し、次の同種の失敗を確認できる回帰ケースへつなぐ。**

読み手がレポートから判断できることは次の3点とする。

- Agentが自分で根拠に気付いて更新したのか、ユーザーの方向づけを受けて更新したのか。
- 更新によって、次に調べること・判断する条件が具体化したのか。
- 指摘した失敗が、その後の実際の応答で減ったのか。未検証なら、その状態も読めること。

最初の成果物は、既存の6軸評価に軌跡を加えた**実会話1件のレポート**とする。そのレポートを人が校正できることを確かめてから、回帰ケースの保存と変更前後の比較へ進む。新しい能力レベルや総合点は作らない。

本書の承認で着手対象とするのは、以下のA〜Cのローカル開発である。実データ送信は既承認の対象・頻度内に限る。現行Cronの実行先切替は2026-10-26にユーザー承認を受けて実施済み。実Agentの比較実行、スキル反映、Gitへの反映は別途の承認対象。

## 4. 最小構成とデータの流れ

```text
既存Hermes会話DB（read-only）
  ↓ 既存の承認範囲・選定上限
送信本文の最小化 + 欠落範囲の記録
  ↓ 同じ一度のClaude Code呼出し
6軸評価 + 問いの軌跡候補 + 訂正候補
  ↓ 型・参照位置・抜粋一致・順序の検査
軌跡付きレポート + 最小JSON
  ↓ ユーザーが根拠を見て回答
人手校正記録 → モデルとの不一致一覧
  ↓ 確認された失敗だけ
回帰ケース候補 → 改善案 → 承認 → 新しい応答で比較
```

### 4.1 評価結果の契約（提案）

現行6軸の名前・4段階ラベルを維持し、新形式には`schema_version`を付ける。詳細なJSON Schemaは実装Aで固定する。旧レポートは書き換えない。

- **評価の識別**：ハッシュ化した会話参照、評価入力hash、評価器版、Rubric版、実行時刻、評価モデル。モデルの実際の応答情報で版を取れない場合は`unknown`を記録し、指定値と実測値を混同しない。
- **入力の状態**：`active_only`、発言の切詰め位置、要約から得た箇所、ツール本文除外、観測した範囲。省略がある入力を「会話全体を確認済み」と表記しない。
- **6軸判定**：`axis / status / reason / evidence_spans`。根拠は発言位置と最小化後本文内の範囲で指定し、短い実在抜粋を機械的に取り出す。
- **問いの軌跡**：`question_initial / question_current / question_changes / decision_impact / next_validation / outcome`。確認できない値は空欄と理由を残す。問いが変わらない会話も有効な入力とする。
- **各更新**：更新前・更新後・理由の根拠位置、先行Evidenceの位置、ユーザーの方向づけの位置、その後の応答・判断の位置を持つ。更新を一つの最終評価へ潰さない。
- **訂正候補**：対象のAgent発言、ユーザーの訂正、直後のAgent行動、失敗軸、期待する行動、次に確かめる条件。原因は`cause_hypothesis`として仮説のまま保存する。

### 4.2 自律性と協働の扱い

新形式では、各更新の観測順序と原因の推定を別項目にする。既存の`causal_order`で使う値名は、新形式の`observed_order`の候補として再利用する。旧形式は変更せず、新形式から旧形式への自動変換は行わない。

- `evidence_agent_update_user_judgment`：根拠が先にあり、Agentの更新、その後のユーザー判断が観測された候補。
- `user_judgment_agent_structuring`：ユーザーの方向づけをAgentが構造化した候補。
- `not_observable`：必要な順序・根拠が取れないもの。

同じ会話に両方あれば更新ごとに表示し、会話全体を一方に丸めない。更新後のユーザー判断がない場合も、見えている途中経過は残す。

保存する項目は次のように分ける。
- `observed_order`：上記の順序ラベルと、それを支える発言位置。機械検査の対象は参照の実在と前後関係であり、各発言の意味分類まで正しいことは保証しない。
- `cause_hypothesis`：何が更新を促したかについてのモデルの仮説と根拠位置。観測だけで説明できない場合はnullと理由を残す。
- `causal_review`：同じ評価参照・入力hash・版・更新位置に結び付く人の確認。`review.json`へ別記し、初期値は`review_status: pending / verdict: null`。回答後のみ`recorded`とし、`supported | rejected | not_observable`および短い理由を保存する。モデルが人の確認済み状態を生成することは認めない。

時刻の前後だけで因果関係は証明できない。レポートも「観測順序」「原因の仮説」「人の確認」を分けて表示する。順序検査が通っても人の確認はpendingのままとし、人がsupportedと答えた場合も因果の実験的証明とは扱わない。ツール本文を見ていない評価者は、Agentの「調べた」という説明を外部検証済みEvidenceへ昇格させない。先行するユーザー介入を見落として自律性を過大評価していないかを必ず確認する。

### 4.3 保存と情報境界

- 生の会話全文、外部評価への入力全文、元セッションIDを新たに保存しない。会話DBのコピーを作らない。
- JSONとMarkdownに残す内容は同じ最小情報から生成する。JSONを正本、Markdownを表示用とし、両方に同じ評価参照・版を付ける。
- 抜粋は既存の240文字上限を維持し、先頭固定から「実際に根拠となった箇所」へ変更する。切詰めた入力の外側を評価者が引用した場合は拒否する。
- URL除去は完全匿名化ではない。氏名・社名・認証情報等の検出と出力検査を設け、秘密情報の疑いがあれば本文を表示せず送信を止める。検出器の万能性は主張しない。外部CLI側の保存・保持条件も、Python側の非保存とは分けて確認する。
- 人手校正はモデル出力を上書きせず、評価参照・入力hash・版に結び付く別ファイルとして保存する。
- 実会話由来のJSON・校正・回帰候補はローカル限定。将来のGit反映前に専用出力サブディレクトリをignore対象とし、対象ファイルを明示してstageする。現行`.gitignore`はPythonキャッシュ等だけで、会話由来レポートを除外していない。
- 新形式の保存先は、提案として`conversation-review-output/<evaluation_ref>/`に固定し、`evaluation.json`・`report.md`・`review.json`・`correction-case.json`を置く。未作成の成果物は空ファイルで埋めない。このディレクトリ全体をignore対象にする。
- 既存のEvidence Gateは`operational-evidence/`と`evaluation-reports/`以下のJSON・JSONLを走査する（`promotion_gate.py:_iter_paths`）。新形式の保存先が走査外であることをテストする。既存Markdownは残し、古い5軸fixtureや厳格Schemaへ新JSONをそのまま流し込まない。
- 評価入力へ渡すroleを明示し、会話中の指示文を評価者への命令として扱わない。要約を使う場合は由来を表示する。現行CLIのツール禁止リストは全ツール無効化の証明にはならないため、採用前に実際のツール無効化設定を確認し、会話中の外部アクセス指示に従わないことを試験する。

### B：人の校正を保存し、誤評価を見えるようにする

**変更対象**

**手順**

- 新しい校正は版2として6軸の欄を必須にし、各欄を`review_status: pending | recorded`、`status: null | pass | partial | fail | not_observable`、短い理由で表す。未回答の`instruction_adherence`は`pending / null`とし、比較対象から除く。
- `recorded`は有効なラベルと理由を必須にする。`pending`にラベルを付けた不整合は拒否する。回答済み軸がゼロなら一致率はnull、比較状態は`awaiting_review`とする。
- 旧版1は従来の5軸完備入力を受け付け続ける。新形式を旧`human_calibration`へ装って渡さず、版2用の読取・比較経路で共通のラベル比較関数を呼ぶ。人間同士とモデル対人間では`comparison_type`を分ける。

**受入条件**
- 同じ評価参照でも入力hash・版が違えば比較を止める。
- モデル判定と人の訂正が別記録として残り、理由の違いを読める。
- モデル結果を見て行った校正には、その条件を記録する。盲検の評価者間一致度とは呼ばない。
- 因果帰属にも訂正を付けられる。協働として有用だった点を消さず、自律性の過大評価を修正できる。

### C：訂正を回帰ケース候補にする

**変更対象**
- 新設する小さなケース出力処理（仮称`export_correction_case.py`）。
- ローカルの回帰候補形式と、入力・期待行動・実観測を分離するテスト。

**手順**
1. 同じ評価出力の訂正候補から、対象発言・訂正・修正後行動・失敗軸を結び付ける。追加のLLM呼出しは行わない。
2. 人が確認した失敗基準のみを回帰ケースへ採用する。追加要望・方針変更・好みの指定だけの発言を、以前のAgent行動の失敗と決めつけない。対象軸以外の未回答を勝手に埋めない。
3. 回帰用の入力は誤応答の直前までの必要最小限の文脈に限定し、正解ラベルや後続の訂正を入力に混ぜない。
4. 根拠が短い抜粋だけでは足りない場合は候補のまま止める。必要な元文脈はHermesが許可範囲内で再確認し、想像で補わない。
5. 原因仮説、変更案、同じ誤りを検出する条件を示す。スキルへの反映は別途承認後。

**受入条件**
- 「謝罪した」「スキルに追記した」だけで改善完了にならない。
- 人が用意したテスト出力は評価器の感度検証と表示する。Agentが改善した証拠に混ぜない。
- `no_go`・保留・意図的延期・安全停止を、一律に失敗ケースとして採用しない。

### D：改善効果の確認と日常運用への反映 — 追加承認後

- 承認された一つの変更について、同じ最小入力を変更前版と変更後版のHermesに与える。モデル、ツール条件、入力、Rubricを揃え、違いを記録する。
- 新しい応答を同じ外部評価者で評価する。評価者へ「改善版だから良くなるはず」と示さない。評価器自身を変更した比較では、前後の応答を同じ新Rubricで再採点する。
- 初回は一組の比較を確認する。これは単一ケースの結果であり、一般的改善や再発ゼロの証明とはしない。利用中の次の同種会話でも確認する。
- 実Agent生成の追加呼出し・外部再評価の費用とデータ範囲を事前に示す。日次上限を実験用コマンドで迂回しない。既存枠外の比較には別承認が必要。
- 採用後、既存の自動選定器に新しいレポート形式を接続する。ローカル実行記録で`no_candidate / daily_cap / locked / evaluation_failed / report_saved`を区別する。候補なしのDiscord通知は増やさない。
- 配信担当は既存Hermes Cronの`no_agent`標準出力→Discord `1547520274029608990`配信とする。評価スクリプトに新しいDiscordクライアント・Webhookは作らない。既存wrapperはv2結果のMarkdown本文を標準出力し、候補なしは無通知、失敗時は本文を含めず状態のみ通知する。設定読戻しは確認済み、実際の投稿は次回Cron実行待ち。
- 保存成功と配信確認を分ける。Cronの成功状態だけで配信済みとせず、実際の投稿を読む。配信を再試行するときは保存済みの安全な通知を使い、Claude評価を再実行しない。
- 旧形式を使う実行入口・版を戻し先として保持する。新形式の解析失敗や未検査出力を検知した場合は当該配信を止め、要点だけを報告する。既存レポートを上書きしない。

## 6. 検証ケース

実装時に以下をテストと実会話校正へ割り当てる。合成fixtureの合格と、実会話での意味判定は別に報告する。

- **ユーザーが方向を変える**：先行する訂正を示し、協働に分類できる。
- **AgentがEvidenceを受けて更新する**：根拠、更新、ユーザー判断の位置を示す。外部根拠の真偽は別に未確認表示できる。
- **一つの会話に両方がある**：更新単位の分類を保持する。
- **更新がない／更新の必要もない**：空の更新列を受理し、自動で失敗にしない。
- **存在しない根拠・未来の根拠**：参照検査で拒否する。空の根拠で`pass`を通さない。
- **本文途中の根拠**：1,500文字以内の途中箇所を正確に抜粋できる。切詰め外は補わない。
- **要約・省略・ツール本文欠落**：因果順序や外部結果を推測で埋めない。
- **肯定と承認**：肯定を購買・成果・権限拡大へ転用しない。
- **未回答と判定不能**：未回答はpending、人が判断不能と答えた場合だけ人のnot_observableを保存する。
- **5軸・6軸の互換性**：旧比較器を壊さず、新形式は型と比較対象を明示する。
- **訂正と改善**：訂正後の謝罪だけのケースを改善成功にしない。後続応答がない場合は未検証。
- **漏えい・送信範囲・重複**：URL、識別子、秘密情報の疑い、別チャンネル、入力上限超過、日次再実行を拒否または除外する。
- **保存・通知失敗**：不完全なJSONを確定しない。保存と通知を別状態にし、通知再試行で評価枠を再消費しない。
- **新JSONとEvidence Gate**：会話評価のJSONが本番Evidenceとして走査・採用されないことを確認する。

実会話の校正は最初の1件から始め、次に構造の違うケースへ進む。必要なのは件数だけの達成ではなく、ユーザー主導、Evidence主導、延期・No-Go、欠落を見分けられるかである。既承認チャンネル内で観測できない構造は未検証として残す。

**固定fixtureで検査する期待値の例（実会話の評価結果ではない）**
- ユーザーが訂正し、Agentがその指示通りに再構成したケース：`observed_order`のラベルは`user_judgment_agent_structuring`、`evidence_driven_update = partial`。独立した発見という表示を含めない。
- 順序の必要箇所が要約だけに残ったケース：`observed_order`のラベルは`not_observable`。他の軸は観測できる部分だけ評価する。
- 根拠→更新→ユーザー判断の順は確認できるが、更新理由が不明なケース：`observed_order`のラベルは`evidence_agent_update_user_judgment`、`cause_hypothesis = null`に理由を付け、`causal_review`は`pending / null`を維持する。順序だけで自律的更新を確定しない。
- 根拠の位置が更新後にしか存在しないケース：構造検査エラー。Agent能力の`fail`へ置換しない。
- 指示遵守のみ未回答の校正：当該軸は`pending / null`、比較対象外。他の回答済み軸の比較は可能。
- 正当なNo-Goのケース：`outcome = no_go`を保持し、その値だけを理由とする失敗判定を出さない。
- 訂正後の新しい応答がまだないケース：回帰候補は作れても改善状態は未検証とする。
