# Measurement-First Capability and Evaluation Design

更新日: 2026-09-15
状態: 採用方針（実装前の設計）

## 1. 目的

Agent Levelの評価項目を増やす前に、現在のコンピューター／Runtimeが何を観測・検知・評価できるかを確定する。

理想的な能力を先に細分化すると、実際には評価できない項目、根拠のないスコア、形式的なチェック項目が増える。したがって、本リポジトリでは **measurement-first** を採用し、評価可能性をLevel契約の前提条件とする。

この文書は、Level 1〜9の定義を変更せず、Capabilityを新設・細分化する際の入口を定める。通常Agent接続、Strict enforcement、Production配信、cron変更、自動昇格は有効化しない。

## 2. 採用する順序

```text
観測可能性の棚卸し
  → 検知可能なイベントの定義
  → 評価可能性の確認
  → Capabilityの定義
  → 実務シナリオへの適用
  → 不足する観測経路の追加
```

Capabilityを先に作り、後から検知方法を探す順序は採用しない。

## 3. 評価の対象レイヤー

### Tier A: 機械的に検知・評価できる

Runtime Traceや決定的Validatorから直接確認できるもの。

- Tool呼び出しの有無、順序、引数
- 実行ステップ、エラー、再試行
- Validatorの実行結果
- Safe-stopや外部副作用の状態
- 成果物の存在、Schema適合、Integrity
- 重複、conflict、保存失敗

### Tier B: Traceは取得できるが意味評価が必要

Traceや会話履歴を材料に、LLM Judgeまたは人間Calibrationを使うもの。

- 調査経路の妥当性
- 複数視点の差分と統合品質
- 反証探索の十分性
- 問いの更新理由
- 次の検証行動の具体性
- 事実、観測、仮説の分離

Tier Bは自動判定だけでPassにしない。人間評価との一致、評価者間差分、誤検知・見逃しを確認する。

### Tier C: 実案件・外部結果が必要

テキストやTraceだけでは完結しないもの。

- 顧客課題への適合
- 実際の意思決定への寄与
- 面談で得られた情報の有効性
- 仮説変更が事業判断を前進させたか
- 改善前後の業務成果

Tier Cは実案件の結果、議事録、成果物、判断記録などを別Evidenceとして紐づける。会話だけで確定しない。

### Tier D: 現時点では評価不能

以下は研究上の仮説として保持できるが、Operational Levelの正式評価項目にはしない。

- 本当に潜在欲求を理解したか
- 本質的に正しい問いだったか
- 長期的にCXOとして信頼できるか
- 社会や組織を変えるほどの価値があったか

評価不能を成功・失敗のどちらにも寄せず、`inconclusive`として保持する。

## 4. Capability採用ゲート

新しいCapabilityまたは評価項目を追加する前に、次を定義する。

```text
項目名:
評価したい行動:
観測データ:
取得元:
検知方法:
評価方法:
人間評価の要否:
成功条件:
失敗条件:
未観測時の扱い:
誤検知・見逃しの確認方法:
Evidenceの保持期間・最小化方針:
```

以下のいずれかが未定義なら、正式なLevel契約へ追加せず、研究仮説として保留する。

- 観測データがない
- 検知方法がない
- 評価基準がない
- 未観測時の扱いがない
- 評価結果を再現できない

## 5. 最小Evidenceモデル

項目を増やす代わりに、まず一連のTrajectoryを保持する。

```text
scenario_id
question_initial
question_current
question_change_reason
evidence_that_triggered_change
question_state
decision_impact
next_validation
evaluation_basis
```

`question_state`の例:

```text
exploring
updated
converging
provisionally_locked
reopened
```

`evaluation_basis`の例:

```text
text_only
conversation_feedback
external_evidence
human_review
inconclusive
```

このモデルは、問いの浅さを直接数値化しない。問いが変わったか、何が変化を引き起こしたか、判断に影響したかを記録する。

## 6. 未観測と失敗の分離

```text
未観測       = 観測経路がなく判定できない
未達         = 観測できたが条件を満たさない
捕捉失敗     = 行動は発生した可能性があるがCollectorが取得できない
評価不整合   = データはあるが評価基準・Evaluatorが一致しない
```

これらを同じ空欄、`blocked`、`failed`にまとめない。

- 未観測: `inconclusive`
- 未達: `failed`
- 捕捉失敗: Collector障害として別記録
- 評価不整合: Evaluator設計の再検討へ送る

`decision`と`side_effect_status`の既存分離、およびShadow EvidenceをProduction Evidenceとして扱わない境界を維持する。

## 7. 問いの探索・更新・収束

「問いの浅さ」は直接の判定項目にしない。正式なCapability候補は次の一つにまとめる。

> 問いを探索し、Evidenceに応じて更新し、判断可能なゴールへ仮固定する能力

観測するのは次の行動である。

```text
初期の問い
  → 新しいEvidence
  → 更新後の問い
  → 更新理由
  → 判断への影響
  → 次の検証
```

ゴールは最初から絶対視しない。事業テーマがある場合は、タイムマシン候補の選定、実績あるビジネスのローカライズ検討、Ozawa式の市場・プレイヤー・成功要因調査を経て、51点・センターピン・ゴールを仮固定する。

この探索は無制限の発散ではない。各問いについて以下を記録する。

- どの不確実性を減らすか
- どの仮説を見分けるか
- 答えによってどの判断が変わるか

これらに答えられないものは、興味深くても現在の検証対象から外す。

## 8. 実務シナリオとの接続

新規事業伴走の実務シナリオは、案件名ではなく、反復可能な意思決定単位として定義する。

基本形:

```text
事業テーマまたは着想
  → タイムマシン候補の比較
  → 成功モデルの調査
  → ローカライズ可能性の分解
  → Ozawa式のマトリクス・反証調査
  → 51点・センターピン・ゴールの仮固定
  → 小さな検証
  → 結果に応じた再オープンまたは収束
```

このリポジトリの評価では、方法論名の存在を能力証明としない。実際のTrace、調査結果、仮説更新、判断への影響を別々に確認する。

## 9. Agent-level汎用能力と事業開発トラックの分離

このリポジトリでは、事業開発で観測される能力を、Agent-level全体の定義と同一視しない。

### 汎用Agent-level能力（ドメイン非依存）

- 目的・制約・判断者を把握する
- 曖昧な問いを分解し、必要な不確実性を特定する
- 事実、観測、仮説、未確認を分離する
- Evidenceに応じて問い・方針を更新する
- ユーザーの訂正・拒否・肯定を区別する
- 次の検証行動と判断分岐を具体化する
- 評価限界と未観測を明示する

### Business Developmentトラック（ドメイン適用）

事業開発では、上記能力を次の構造で観測する。ただし、これはagent-levelの唯一の評価定義ではない。

```text
最低限達成すべきゴール（51点の候補）
  → 打ち出し角度
  → センターピン
  → 根源的欲求との接続
  → 仮説・小さなテスト
  → 最低限のEvidence
  → 組織的投資・事業化・独立・カーブアウト・終了の判断材料
```

ここで51点はPMFや事業成功の証明ではなく、現時点の体制で実証でき、経営層が次の組織形態・投資判断を行える最低限の意思決定可能性という作業仮説である。根源的欲求、最終的な事業成果、組織形態の妥当性は、構造化Traceだけで自動確定しない。

このトラックは、実会話ケースで再構成し、`observed`、`inferred`、`not_observable`を分けて検証する。OzawaやTSUNAGUの方法論名が存在すること自体は、能力の証拠にしない。

## 10. 評価器の成熟順序

```text
1. 決定的なSchema / Trace検証
2. 固定シナリオのBehavior評価
3. LLM Judgeの人間Calibration
4. 実案件のOutcome紐づけ
5. 改善前後の比較
6. 複数ケースでの再現性確認
```

上位段階の証拠がない限り、下位段階の成功を上位Capabilityの証明へ昇格させない。

特に以下を分離する。

- Skillやツールが存在すること
- 固定シナリオで動作すること
- 実運用で役に立ったこと
- 継続的に改善したこと

## 10. Capability拡張の判定

既存の観測経路で十分に取得できないCapabilityは、まず観測経路の改善候補にする。Capability契約の追加は、その後に行う。

```text
観測できない
  → Collector / Trace不足か確認
  → Evaluator不足か確認
  → 実世界Evidence不足か確認
  → それでも評価不能なら研究仮説として保留
```

理想能力を細かく分解して評価項目を増やすことは、測定可能性が確認されるまで行わない。

## 12. 完了条件

本方針を実装フェーズへ進める条件:

- 観測可能性インベントリが作成されている
- 各観測対象の取得元と保存境界が明確である
- 機械判定と人間評価が分離されている
- 未観測・未達・捕捉失敗・評価不整合が区別されている
- 固定シナリオでEvidence生成からReportまで実行できる
- 新しいCapabilityを追加する採用ゲートが機能している
- Production接続、自動昇格、cron変更を伴わずにShadow検証できる
